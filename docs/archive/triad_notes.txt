So, this would now give each one of the modular components an interface which fully describes its exterior behavior, allowing us to make its interior an adaptive black box if we needed to.  We could lock the whole relationship with zero-knowledge proofs if we wanted to even.  

This gives each component an interior - which itself might be utilizing other components within to implement the internal functions.  We could extend this example by showing the internal economy of any one of these modules, showing how it is computed through the various substeps in signamancy if we wanted to here.  Signamancy may actually be a fairly efficient language for utilizing the GPU (we have a parser+compiler+execution engine in another project built to pack these types of operations and run them all simultaneously in a fast cycle of identical steps), so it may actually make sense to do that computationally.  

I'm now pondering what the transitions between exterior signals and interior signals should look like.  Perhaps it should be seen like they go through a "cell wall" where they enter an interior economy detached from the exterior (a different state), and then can be picked up by internal processes in a similar parallel lazy way like chemical reactions.  the interior calculations continue that way until they produce output values - and only the ones specified in the initial contract (neurotransmitters A + B => B + D) can output again (B + D).   We cant have those be instant, as we need the interior to actually do computation, so we're stuck either waiting for traditional compute (usually CPU) to finish, or we do it all with signamancy causal rules internally too, but design in a way that inevitably chains conditions to produce the output, and that's just a requirement of the function (else it's an error, and punished by revision). 

This does allow any of these modular functions to split itself into time-critical operations necessary for output immediately and slower side-effect operations that can go slower though, and use subsequent layers within the interior to immediately pass outputs to its contract and then have interior layers continue the pattern asyncronously with slower updates.  e.g. passing a file write promise and then following through with the actual write slower.  That would have to be part of the contract though if the nuance matters anywhere else.  More likely, it'd be for things like internal economics of the function, storing logs, self-training, etc etc which the exterior doesnt care about. 

It would also probably arise in computation budgets and actual currency-based economics of these interiors in relation to each other, since they're capable of self-managing, but still need to have some relationship to external scarcities.  When there is no scarcity of a resource or it doesnt matter much, then such things can be lax, but when it matters there needs to be accounting.  Such things would likely be managed though the signamancy contract as well, or a separate contract - as we could have multiple contracts utilizing the same module in different ways, or fueling it with compute credits.

Small/simplified economies can be entirely worked out and solved for.  Larger ones cant.  This is a pretty good argument for layering things and keeping complexity contained so it only needs to be thought about for the interplay of one interior at a time.  The quintessential safest one is a single layer per operation, which is sequential computation - or in functional programming, currying.  However, since we can do parallel operations easily in gpu this is rarely the most efficient, and since we have an economy of growing and changing modules it may not be the best development strategy either to be so heavy handed.   Even if the cost is not having full understanding of every possibility in an economic zone, we can still gain confidence in particular paths or in the most common operations, and we can still make guarantees anywhere we need to by making an impermeable barrier contract seal to everything except what we allow through.
